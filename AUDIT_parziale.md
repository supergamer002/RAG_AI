# AUDIT — RAG_AI / Nexus dashboard

Audit incrementale del progetto contenuto in `rag.zip`: libreria Python `rag/` (ingest → index → retrieve → generate → eval),
backend FastAPI in `webapp/backend/main.py`, frontend React/Vite in `webapp/frontend/`.

**Metodologia**: in questo ambiente non ho un browser reale, quindi "premere ogni bottone" viene simulato così:
1. leggo ogni componente React e mappo ogni bottone/azione all'handler e alla chiamata API corrispondente;
2. avvio backend (uvicorn) e, dove possibile, frontend (vite build/dev) per verificare che partano;
3. chiamo ogni endpoint REST che un bottone invoca, con dati reali (incluso ingestion dei 2 sample), verificando risposta, stato DB, side-effect;
4. leggo il codice Python sottostante (ingest/index/retrieve/generate) per individuare bug non necessariamente visibili a runtime con dati piccoli.

Ogni anomalia trovata viene aggiunta come nuova riga cronologica qui sotto, con: **componente**, **severità**, **descrizione**, **evidenza**.

Legenda severità: 🔴 Critico (crash/dati corrotti/sicurezza) · 🟠 Alto (funzione rotta) · 🟡 Medio (comportamento sbagliato non bloccante) · ⚪ Minore (cosmetico/refactor).

## Log anomalie

- 🟡 **webapp/backend/main.py** — Il file usa sintassi f-string introdotta da PEP 701 (Python 3.12+): apici doppi annidati identici all'esterno (riga ~170, campo `dimensions`) e backslash dentro l'espressione `{...}` di una f-string (righe ~470-474, filtri `fonte_titolo`/`tipo_fonte`/`sezione` in `/api/chunks`). Nessun file del progetto (README, requirements, .bat di avvio) dichiara un vincolo di versione Python. Su Python 3.10/3.11 (ancora molto diffuso, incluso in WSL, citato nel commento del .bat) questo file **non si importa nemmeno** (SyntaxError), quindi l'intero backend non parte. Verificato con `ast.parse`: passa solo su Python 3.12.3 (versione disponibile in questo ambiente).
- 🟡 **webapp/backend/config.json (shipped)** — Il config di default distribuito ha `"chunkOverlap": 72` (interpretato come percentuale in `_esegui_ingestion_job_sync`/`esegui_ingestion_batch_job`, cioè `overlap_pct/100.0` → 72% di overlap tra chunk consecutivi). Il fallback hardcoded in `main.py` (`SETTINGS_DEFAULTS`) usa invece 15%. Un utente che fa il primo ingest senza toccare le Impostazioni ottiene quindi chunk con il 72% di testo duplicato l'uno con l'altro: storage gonfiato e recall/rerank degradati da near-duplicate massiccio. Sembra un valore inserito per errore (forse pensato in altre unità) mai allineato al default "corretto" di 15.
- 🟡 **GET /api/documents (mappa_chunk_item / get_documents, main.py ~L376-377)** — `doc_type` è calcolato da `Path(path_str).suffix.upper()` ma è accettato solo se in `["PDF","DOCX","PYTHON","YAML","MARKDOWN"]`, altrimenti forzato a "PDF". Dato che `SUPPORTED_INGEST_EXTENSIONS = {".pdf", ".json"}`, ogni documento ingerito da JSON (estensione reale "JSON") **non è nella whitelist** e viene mostrato in UI come tipo "PDF" — etichetta doc-type sbagliata per tutti i file JSON ingeriti, il tipo di file più comune per l'ingestion "from_units".
- 🟠 **rag/index/db_manager.py (`BASE_DB_DIR`, riga 23) + webapp/backend/main.py (`caricaconfig`)** — `DatabaseManager` usa una costante hardcoded `BASE_DB_DIR = Path("data/databases")` e non legge mai `config["storagePath"]`. La Settings UI (e il file `config.json`) espongono ed accettano un campo "storagePath" validato e salvabile (`PUT /api/settings`), ma modificarlo **non ha alcun effetto**: `db_manager` è un singleton istanziato una sola volta all'import del modulo, e persino `POST /api/system/restart` (che dice esplicitamente di "ricaricare configurazione e risorse RAG") ricrea solo `embedder`/`reranker`/`generatore`, MAI `db_manager`. Il valore di default del fallback in `caricaconfig()` (`"rag/index/store/lancedb"`) è anche diverso dal valore realmente in uso (`"data/databases"`), rendendo la situazione ancora più confusa per chi legge il codice. Impostazione "morta": l'utente crede di spostare lo storage e non succede nulla, nemmeno dopo riavvio del backend (perché il path resta comunque quello hardcoded, relativo alla cwd del processo uvicorn).
- ⚪ **rag/retrieve/hybrid_search.py riga 146** — Stessa sintassi f-string PEP 701 (backslash dentro `{...}`) della riga ~470 di `main.py`: `f"'{cid.replace('\'', '\'\'')}'"`. Altra occorrenza dello stesso vincolo implicito su Python 3.12+, non documentato da nessuna parte (vedi voce precedente).
- 🟡 **rag/retrieve/rerank.py (`_calcola_punteggi`/`_ordina_per_punteggio`)** — `FlagReranker.compute_score(coppie, normalize=True)` restituisce, per contratto documentato della libreria FlagEmbedding, uno **scalare float** (non una lista) quando `len(coppie) == 1` (vedi implementazione ufficiale: `if len(all_scores) == 1: return all_scores[0]`). Con un solo candidato da rerankare (DB quasi vuoto, o `topK`/numero di chunk recuperati pari a 1) `punteggi` è un float, e `zip(candidati, punteggi)` in `_ordina_per_punteggio` solleva `TypeError: zip argument #2 must support iteration`. L'eccezione è silenziosamente inghiottita dal blocco `except Exception` in `_esegui_query_su_tabella` (main.py), quindi l'utente non vede errori ma il reranking semplicemente non avviene (rerankScore resta 0.0/non calcolato) — bug silenzioso di qualità, non un crash visibile, riproducibile ogni volta che il set di candidati ha esattamente 1 elemento.
- 🟡 **rag/generate/answer.py + webapp/backend/main.py** — Il modello di generazione (`qwen3:8b`) è hardcoded in `MODELLO_GENERAZIONE` e `OllamaGenerator` viene istanziato in `main.py` (righe 122 e 945) **senza mai passare `modello=`**. A differenza di `embeddingModel` e `crossEncoderModel`, non esiste nessun campo "generationModel" né in `config.json`/`SETTINGS_DEFAULTS` né nella Settings UI: l'utente non ha alcun modo di cambiare il modello di generazione dalla dashboard, anche se la UI dà l'impressione di controllare l'intera pipeline (embedding + reranker + generazione) dalla stessa schermata.
- ⚪ **webapp/frontend/src/data/mockData.ts** — File di 367 righe con dati finti (documenti, chunk, telemetria, ecc.) non è importato da **nessun** componente del frontend (verificato con grep su tutta `src/`). Codice morto, probabilmente residuo dello scaffold iniziale (AI Studio/Gemini template, coerente con `@google/genai` in `package.json` mai usato altrove): confonde chi legge il repo pensando che l'app abbia ancora una modalità demo/offline.
- ⚪ **webapp/frontend/package.json + .env.example** — La dipendenza `@google/genai` e le variabili `GEMINI_API_KEY`/`APP_URL` documentate in `.env.example` non sono referenziate da nessun file `.ts`/`.tsx` del frontend (grep su tutta `src/` non trova nulla). Sono residui del template "AI Studio" da cui il progetto è partito; oltre al peso morto in `node_modules`, `.env.example` induce l'utente a pensare (erroneamente) che serva una API key Gemini per far funzionare l'app, che in realtà usa solo Ollama locale.
- 🔴 **Progetto — dipendenze mancanti per il backend FastAPI** — L'unico file di dipendenze presente è `rag/requirements-ingest.txt`, che copre solo il layer di ingestion (docling, lancedb, pyarrow, tantivy, FlagEmbedding, pypdf, umap-learn) e dichiara esplicitamente nel commento: "il resto dello stack ... avrà il proprio requirements quando sviluppato". Quel requirements per lo stack "resto" **non è mai stato creato**, ma `webapp/backend/main.py` (1480 righe, completamente sviluppato) importa `fastapi`, `starlette`, `pydantic`, e l'endpoint `/api/vectors/project` (Vector Explorer, metodi t-SNE/PCA/KMeans) importa `numpy` e `sklearn` — nessuno dei quali è elencato in nessun file di dipendenze del repo. Un clone pulito che segue `avvia_dashboard.bat` (che assume solo Node.js come nuovo prerequisito, "non usato altrove nel progetto") e installa solo `requirements-ingest.txt` **non riesce nemmeno ad avviare `uvicorn`** (`ModuleNotFoundError: fastapi`), e anche dopo aver indovinato fastapi/uvicorn a mano, il Vector Explorer con metodo tsne/pca crasha per `sklearn` mancante. Nessun `requirements.txt` completo, `pyproject.toml` o `environment.yml` esiste nel repository.
